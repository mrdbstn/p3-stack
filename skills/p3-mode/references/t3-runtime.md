# T3 runtime contract

This adapts pstack's mechanics to T3. Preserve its design, verification, ownership, and operator gates. The reviewed compatibility baseline is stable T3 Code v0.1.11, pinned in `t3-runtime.lock.json`. Nightly builds are optional and must not add requirements absent from stable. Tool availability is a runtime fact. Check the actual tool schema and `orchestrator_capabilities` before using a capability. An unavailable tool is a reported limitation, never permission to skip proof.

Tools that act as the calling T3 thread, including `delegate_task`, `task_status`, `task_cancel`, `create_threads`, and `request_secret`, are hidden from outside MCP clients without that thread context. A missing tool is not fixed by guessing a name or changing credentials. Keep work within the capabilities actually exposed; do not replace internal delegation with a top-level conversation without the user's explicit request.

## Paths and installation

Detect the running environment before selecting a shell or tool. In WSL/Linux, use native Linux tools through PATH and keep repositories and dependency stores under the Linux home directory. Do not invoke Windows executables or use `/mnt/c` as the checkout or dependency store. On native Windows, use no-profile PowerShell and tools through PATH. Skills must be installed in the same environment and user account where the agent runs.

Resolve bundled files from the absolute path of the installed skill, not the project working directory. From any leaf skill, p3-mode is `../p3-mode/SKILL.md`. From p3-mode, its scripts are `scripts/` and its playbooks are `playbooks/`. Pass absolute paths to children. The Comment Sicko prompt is bundled with no-comments at `references/comment-sicko.md`. No installed skill depends on the repository-root `agents/` folder.

The first line of every delegate's brief is `Read <absolute-p3-mode-path>/worker.md before anything else.` Resolve that pointer from the installed skill, and propagate it when a child starts another agent. The operator is the user, not the coordinating agent. A complete T3 brief carries the task's bar, scope, evidence pointers, and standing orders because no parent history is inherited. A kickoff cannot override user permissions or operator gates.

When a playbook says to re-read its trunk version, that trunk belongs to the skill checkout. Resolve that checkout from the installed file and use `git -C <absolute-skill-repo> show origin/main:<skill-path>` when the ref is available. The target application's trunk need not contain any p3-stack files. Otherwise re-read the installed version and record that limitation.

Read project-root `p3-models.md` at task start. If absent, read `~/.agents/p3-models.md`. The project file wins. An absent role, `auto`, or `inherit-parent` inherits the parent target. Configure a panel with `/setup-p3` before promising model diversity. Installing a skill does not invoke it; use `/p3-mode` for rigorous tasks, or invoke individual skills.

## Models and effort

Each configured entry names a provider instance, model, and optional effort. Resolve these against the live catalog. `orchestrator_capabilities` returns a short list; use its `search` input for configured or other catalog models absent from that list. Pass `target: {providerInstanceId, model, options}` using only option keys and values actually advertised for that model. Never invent a model slug or attach a reasoning suffix to a model ID. Omit the target for `auto` or `inherit-parent`. A rejected entry is not retried; use the calling skill's valid same-family fallback, or inherit only when that skill allows it, and report the change. Never replace Arena's different-vendor judge with the parent's vendor.

The configured budget is the starting effort. Panel seats keep their listed effort. Raise other roles one supported step, up to xhigh, for the hardest work, lower one step for ordinary judgment and two for routine mechanics. No explicit role runs above xhigh. Gemini seats are capped at high even if Neon advertises xhigh; lower budget targets still apply. Keep its configured provider and family. Opus 5.5 uses its advertised fast option whenever available, not only for urgent work. Verification keeps the configured swarm model. Omit unsupported effort or speed options and report that limit. Never retry invented options or a rejected target.

Delegated results and thread runs can report `executedModel`, the model the provider says actually ran, separately from the requested `model`. Record both when they differ. Use the reported execution model when checking panel-family diversity and Arena's vendor gate. This field can be absent or null, especially on older linked environments; say when actual-model diversity could not be verified rather than inventing it. A judge reported to have run on the parent's vendor does not satisfy Arena's cross-judge rule.

Group families by the model's prefix, independently of its provider instance. For a namespaced catalog ID, classify the model component but pass the complete catalog ID unchanged in `target.model`. Strip a leading `cursor` prefix component before comparing, and use the longest matching prefix: `claude` followed by `fable` is the Fable family, other `claude` models are the Claude family, and `gemini` is its own family. Any other model's family is its text before the first hyphen, so unfamiliar prefixes do not collapse into one family. A vendor is a family except that Fable and other Claude models are one vendor. Distinct provider instances alone do not establish either kind of diversity; a shared provider can host different model vendors.

Setup prefers detected Opus 5.5 for code, prose, judgment, and workers, with Fable 5.2, Opus 5.5, and Gemini 4 Neon for runner panels. The default judge pool uses Opus and Gemini 4 Neon. Outside panels, Fable requires the user's request for this task or two Opus 5.5 xhigh runs of the same brief failing their check; difficulty alone does not qualify. Model names are discovery preferences, not fabricated IDs or guaranteed availability. Preserve user choices except the source's explicit migrations, and report unavailable models or qualifying evidence. Setup replaces non-Neon Gemini 4 entries only in arena runners, arena cross-judge pool, and interrogate reviewers, in every file including defaults 3, using detected Neon targets. It lists replacements and unresolved choices in its existing review; aliases and other roles/models stay. The `large` budget keeps each role's starting effort, `medium` lowers one step, and `small` lowers two, capped at xhigh and high for Gemini. Setup also migrates unlimited to large and drops retired roles under `# defaults: 3`; it does not guess which other catalog targets were deliberate choices.

## Delegation and isolation

Use `delegate_task` with `mode: "async"` and a complete brief. Children receive only that brief, not parent conversation history. Include the outcome, exclusive scope, acceptance checks, absolute file pointers, standing orders, prior findings, and report shape. Do not launch a child merely to run the parent's entire playbook.

Code writers, competing implementations, and live verifiers use `isolation: "worktree"` when this field is supported. T3 creates the checkout from the parent's current local commit, runs project setup, and binds the child before execution. Uncommitted changes are not copied. Commit required inputs first. Name a child-owned branch before it writes or pushes. Read-only investigators may use `isolation: "shared"`. Never run concurrent writers in the same checkout, even on disjoint files if they can change shared refs or run Git commands.

If isolated delegation is unavailable, serialize writers in the owned checkout or report the limitation. Do not silently turn an internal subtask into a separate conversation. Both `create_threads` and `t3_thread_launch` require an explicit user request for ordinary top-level threads. When authorized, bind the requested workspace before starting and follow the exposed schema. `t3_thread_launch` uses `message`, `modelSelection`, and `workspaceStrategy`, not delegation's `task`, `target`, and `isolation`. Pass the intended strategy explicitly. In stable 0.1.11, an outside caller's omitted strategy follows the project's worktree default; an omitted `startFromOrigin` follows its new-worktree setting. Other omitted strategies can still use the project root, not the parent's worktree. Honor a requested base; independent worktrees use the remote default branch with `startFromOrigin: true`, while required unpublished or dependent commits use their local base with `startFromOrigin: false`. An explicit new branch must not already exist. Retry a lost launch reply with the same `clientRequestId`; never launch a duplicate to check progress.

Async completion wakes the parent. Continue independent work, then end the turn when none remains; do not poll or spawn a watcher. A task in `starting` has not begun its provider turn and is not evidence of progress or failure. Call `task_status` only after the task completion wakeup, to consume its final result. Stable T3 forbids polling a running task. Reconcile pending work from durable evidence and scoped thread activity after interruption. A wait-mode timeout, capped at 45 seconds, does not cancel work; this port uses async delegation. Check pending questions with the pending-request tools. Fresh review rounds and fix rounds use fresh tasks with consolidated context and distinct retry keys. Never use a completed task's original result as evidence for a later round.

`t3_thread_send` can start a new provider session in an existing thread with `freshContext: true`. It is not a clone of a worker's built state and never steers the current session. Use it only when a context reset is intended and the current tool schema permits it; keep fresh independent work on `delegate_task`.

## Secrets needed by the task

When authorized work needs a secret only the user can supply, use the available `request_secret` tool instead of asking them to paste it into chat. Request one value per private card; put a sign-in or setup link in `url`. Use a returned one-use `secretRef` only with a tool that accepts it, or request `delivery: "file"` and read the private file only inside the command that needs it. Never place secret text in `delegate_task.task`, reports, or logs. A secret pasted by the user in this thread can be handed to `request_secret` through its supported `value` field for a child or script; never retrieve one from an old thread. Respect a declined request and do not ask again. After cancellation or timeout, request again with a new retry key only if it is still needed. Missing secret-request tooling is a capability limitation, not permission to expose a credential.

## Pull requests and wakeups

Prefer stable T3's native forge tools when exposed for the active thread/project: `pull_request_read`, `pull_request_list`, `pull_request_create`, `pull_request_update`, `pull_request_respond`, `pull_request_review`, `pull_request_merge`, `ci_logs`, and `ci_rerun`. Check the forge, environment, and write capabilities; their presence never expands the user's authorization. Use `gh` for GitHub operations absent from the native schema or when the tools are unavailable, and report that fallback. CLI examples in playbooks describe that fallback, not a requirement to bypass available native tools. Git checkout, push, and rebase still use Git in the owned workspace.

Read PR `summary`, `checks`, `conversation`, and `diff` as needed. Follow each result's `nextCursor`, and report `truncated`, `moreComments`, or truncated CI logs as evidence gaps until resolved; a summary or one page is not a complete patch/review audit. `pull_request_list` is the repository inventory, distinct from this thread's linked PRs. `pull_request_create` uses the thread's pushed branch, links it, and can return an existing PR with `created: false`. Use `pull_request_respond` with `reviewThreadId` for a review-thread reply/resolution; omit it for a conversation comment. If the reply posted but resolution failed, retry resolution without `body` to avoid duplicate comments. Reviews, replies, reruns, and merges are not safe to retry blindly.

For an authorized merge, pass the reviewed current `summary.headSha` as `expectedHeadSha` and confirm the resulting state and base. `auto` can include later pushes and can return an open queued PR; neither arming it nor a successful request proves a merge. `stack` includes lower layers, so never use it to bypass per-PR proof or the verified run's ceiling. Prefer the existing bottom-up, one-PR-at-a-time workflow. Tool availability does not waive verdicts, CI, operator gates, or one writer per branch.

The parent owns PR links and watches. Link each PR with `link_pull_request` unless creation already linked it in the parent thread, and inspect stack order with `list_thread_pull_requests`, cross-checking current native forge or `gh` state. Native creation by a child links that child's thread; the parent still links the returned PR in its own thread. Page the linked list with `cursor=nextCursor` until null when the task needs the full inventory; its optional `states` filter narrows the requested states. Thread summaries show at most five open PRs, watched first, and are not a complete PR list. A child returns its URL, branch, head SHA, evidence, and triage findings to the parent. A child cannot call `watch_pull_request`; neither fresh delegation nor worktree isolation changes that restriction.

The parent handles existing comments before arming `watch_pull_request`, then ends its turn. On a wake it re-reads the PR and checks readiness itself. Route code changes through the single owning writer. A wake does not authorize a merge. Use `unwatch_pull_request` before handing work back. Stable 0.1.11 wakes on observed external or asynchronous merge/closure before ending the watch; an immediate merge/close by the agent can suppress the redundant wake, so read the operation's result. Older linked environments may omit merge wakeups. Confirm live merge into the intended base before advancing. Watches stay active across ordinary wakes; do not re-arm them after every push or CI rerun.

Use `schedule_task` with a structured schedule object for an authorized autonomous run's audit or recovery when the linked environment lacks merge wakeups or a durable audit is otherwise required. Do not add a duplicate merge poll solely because an older baseline lacked the wake. Bind the schedule to the coordinator thread and include the done predicate, durable store, recovery checks, and stop condition. Keep unchanged audits quiet. Record the returned schedule ID and next run time. Delete the schedule on completion or an explicit stop. A PR watch is not a generic watcher for arbitrary refs or external events; those need an appropriate supported integration or a scheduled check.

Set `bindToCurrentThread: true` explicitly for a coordinator-bound task. On creation, an omitted binding defaults to the current thread only in its own project; cross-project creation defaults unbound, and updates retain the existing binding. A webhook's bearer URL is returned only on creation when remote access and run permission allow it. Lists and updates omit it, so absence there does not mean the tunnel is down. Existing URLs can be copied from Settings; never fabricate one or expose it to a child, browser, or public log.

Stable T3 also supports `freshSession: true` on a scheduled task: runs use one thread but start a fresh provider session without earlier runs' context. Leave this off for a coordinator that depends on its ongoing conversation. Use it deliberately for independent repeatable runs only when their prompt and durable records carry everything needed. It is distinct from `bindToCurrentThread`; use the exposed MCP fields rather than the internal storage `threadMode` field. Do not change an existing task's context mode merely because a new release supports it.

## Proof and history

Drive the actual surface with available `preview_*` browser tools, `device_*` simulator tools, a repository control skill, PTY tooling for CLIs, or HTTP for services. Capture actions, resulting state, and side effects. Do not substitute compilation for behavioral proof. Missing tooling stays a verification gap.

List only the active project's threads with `t3_thread_list` (`allProjects: false`), optionally using `titleContains`. When available, `t3_thread_search` can search active thread titles, branches, PRs, project, and message text. Pass the active `projectId` explicitly: an outside caller's omitted project can search all projects. Search skips subagents and is not exhaustive, so a miss is not proof of absence. On older linked environments, fall back to scoped listing and local search of read content.

Read relevant content with paginated `t3_thread_read`. Its default page is newest first; walk older pages with `beforePosition=earlierPosition`. For an audit from the beginning, start with `afterPosition: -1`, then pass `afterPosition=nextPosition` while `hasMore` is true. Page cut-off text with `itemId` and `textOffset=nextTextOffset`; the per-item character cap is 20,000. Do not mistake the newest page for the whole thread. Keep reads restricted to the current project and explicitly requested threads, and use activity view for tool-call evidence. Optional pin, background-task, and wait-state fields may be absent on older linked environments; absence does not prove an idle or unpinned thread. A summary does not prove a file was read. Never mine unrelated projects' session folders.

## Plans and recovery

Upstream 0.15.43 removes Orchestrate and the executable plan checker. Use the current multi-phase planning playbook for a plan, and figure-it-out for large, cross-cutting, or unattended work. Preserve its unit/live/perf evidence and explicit operator gates. Keep task IDs, current PR heads, and evidence outside disposable worktrees where the workflow needs recovery; reconcile them with live state after interruption. Do not recreate a retired workflow or treat handwritten status as proof.
