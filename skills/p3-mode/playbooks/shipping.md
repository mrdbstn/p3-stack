### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then verify each PR independently before it lands.** Prefer the native PR tools in [the T3 runtime contract](../references/t3-runtime.md), with GitHub CLI (`gh`) as the fallback. Link every PR to the parent thread unless creation already linked it. Never require Graphite (`gt`). One independent `delegate_task` verifier per PR, with `mode: "async"` and `isolation: "worktree"`, runs the change the way a user would with the matching control skill (available preview/device tools, a PTY, or the repository verification harness), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Merge the run's lowest unmerged PR using `pull_request_merge`, `method: "squash"`, and the reviewed current `expectedHeadSha`; use `gh pr merge <pr> --squash --match-head-commit <sha>` when unavailable. Do not use `stack` to skip these per-PR gates. A PR based on its parent's branch lands there, not trunk. Read the result back with `pull_request_read` summary or `gh pr view <pr> --json state,mergedAt,baseRefName`; an open queued or auto-merge request is not a merge. A landed PR reads merged with trunk as its base. Arm native `auto` or CLI `--auto` only where the verdict covers the current head, recognizing that later pushes can land too. After a merge lands, retarget the next dependent PR to trunk (CLI `gh pr edit <pr> --base <trunk>` where needed), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. The parent arms `watch_pull_request` with `until: "merged"` on the bottom PR and ends the turn, so owned merge work does not return to the inbox merely because checks finished. Omit that field only on an older linked runtime that lacks it and report the limit. A delegated verifier never owns a watch. Stable 0.1.11 wakes on observed merge or closure; use a coordinator-bound recovery schedule only for an older linked runtime or a separately required durable audit. On every wake or audit tick, read the live PR summary/checks with native tools or the CLI fallback and require confirmed merge into trunk before advancing. Cancel any recovery schedule and unwatch when the verified run finishes or the operator stops it. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
